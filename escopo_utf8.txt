DOCUMENTO DE ESCOPO TÉCNICO
Aplicação Web Local de BI Operacional Integrada ao Trello
Dashboard Builder em HTML, CSS e JavaScript — funcionamento 100% local
Observação importante: 
o dashboard NAU já desenvolvido deve ser utilizado apenas como referência visual e funcional para um template inicial. A nova aplicação deverá ser genérica, local e configurável, permitindo que cada núcleo ou gerência conecte seu próprio quadro do Trello, modele os dados e crie seus próprios KPIs e gráficos.
1. Visão geral do projeto
O projeto consiste no desenvolvimento de uma aplicação web local, construída com HTML, CSS e JavaScript, para criação de dashboards operacionais conectados ao Trello. A aplicação deverá funcionar sem servidor próprio, sem backend e sem banco de dados online. O usuário abrirá a aplicação no navegador e realizará localmente a conexão com o Trello, a importação dos dados, a modelagem das etiquetas/listas/campos e a montagem dos painéis.
A proposta é criar uma experiência parecida com um Power BI simplificado e direcionado ao Trello: o usuário não recebe apenas um dashboard pronto; ele consegue escolher quais informações deseja exibir, como agrupar os dados, quais filtros aplicar, qual tipo de gráfico utilizar e como organizar visualmente os quadros para apresentação.
1.1. Premissas obrigatórias
A aplicação deverá funcionar 100% localmente no navegador do usuário.
O projeto deverá ser desenvolvido com HTML, CSS e JavaScript puro ou com bibliotecas front-end locais.
Não haverá backend, servidor de aplicação ou banco de dados remoto na primeira versão.
As configurações do usuário deverão ser salvas localmente no navegador, preferencialmente via LocalStorage e/ou IndexedDB.
O acesso ao Trello será feito diretamente pelo navegador usando API Key, Token e Board ID informados pelo usuário.
A aplicação deverá permitir importar um arquivo JSON exportado do Trello como alternativa ao uso da API.
A estrutura do Trello não poderá ser fixa, pois cada núcleo ou gerência poderá usar listas, etiquetas e campos de forma diferente.
2. Problema a ser resolvido
Diferentes núcleos e gerências utilizam o Trello com estruturas próprias.
As listas, etiquetas, nomes de status, prioridades e tipos de demanda variam de quadro para quadro.
Um dashboard fixo exige manutenção manual sempre que outro setor desejar utilizar a solução.
A gestão precisa de indicadores visuais, mas cada setor precisa ter liberdade para montar o painel conforme sua própria forma de apresentação.
A solução deve evitar dependência de servidor, instalação complexa ou infraestrutura externa.
3. Solução proposta
Criar uma aplicação web local com três grandes camadas:
Coleta de dados do Trello: via API ou importação de JSON local.
Modelagem dos dados: associação manual de listas, etiquetas, membros e campos personalizados a conceitos de gestão.
Construção visual de dashboards: criação de KPIs, gráficos, tabelas e relatórios visuais configuráveis pelo usuário.
A aplicação não deverá interpretar automaticamente que determinada etiqueta significa prioridade, unidade, origem ou porte. Ela deverá mostrar ao usuário os dados encontrados no Trello e permitir que ele associe cada informação a grupos de análise. Exemplo: a etiqueta “Urgente” pode ser associada ao grupo “Prioridade”; a etiqueta “PSMECOL” pode ser associada ao grupo “Unidade Prisional”; a lista “Finalizado” pode ser associada ao status “Concluído”.

6.2. Regra fundamental
O sistema não deve criar KPIs diretamente baseados no nome fixo da etiqueta ou da lista. 
O KPI deve ser criado com base no grupo modelado pelo usuário. Exemplo correto: contar cartões cujo grupo “Prioridade” seja “Alta”. Exemplo incorreto: contar cartões com a etiqueta fixa “Prioridade Máxima”.

11. Segurança e limitações do funcionamento local
Como não haverá backend, algumas limitações precisam ser tratadas com clareza na interface e na documentação do sistema.
A API Key e o Token informados pelo usuário ficarão no navegador durante o uso da aplicação.
Não se deve deixar API Key e Token fixos dentro do código-fonte HTML/JavaScript.
O sistema deve oferecer a opção “não salvar token”, usando a credencial apenas durante a sessão.
Se o usuário optar por salvar localmente, a aplicação deve exibir aviso de segurança.
O armazenamento local do navegador não é equivalente à segurança de um backend com criptografia e controle de acesso.
Em computadores compartilhados, recomenda-se não salvar token localmente.
Deve existir botão para apagar credenciais salvas, limpar cache e excluir dados locais do ambiente.
A aplicação local não terá controle multiusuário real na primeira versão.
A aplicação local não terá sincronização automática entre computadores, salvo se o usuário exportar/importar o JSON de configuração.

13. Regras de criação de KPIs
Todo KPI deve ter uma fonte: cartões, listas, membros, etiquetas, checklists ou campo personalizado.
Todo KPI deve ter uma operação: contar, somar, calcular percentual, média, mínimo ou máximo.
Todo KPI poderá ter filtros próprios.
Todo KPI poderá ser usado em mais de um visual.
Os KPIs deverão preferencialmente usar os campos modelados pelo usuário, e não nomes fixos do Trello.
O usuário deverá poder duplicar um KPI para criar variações.

17. Observação final ao programador
O objetivo principal não é criar um dashboard fixo, mas uma ferramenta local para criação de dashboards a partir do Trello. O dashboard NAU existente serve como inspiração de layout, gráficos e indicadores, porém a nova aplicação deve ser genérica, flexível e baseada em modelagem feita pelo próprio usuário. A regra de ouro do desenvolvimento é: importar os dados brutos do Trello, permitir que o usuário modele esses dados e só depois gerar KPIs e visualizações.
